# 洋葱穿搭 OnionFit · 核心业务逻辑说明（设计输入）

> 本文只描述这个产品**在替用户做哪些判断、有哪些事实和状态**，不含任何现有界面。
> 现有实现长什么样与本次设计无关，请当作空白重新设计。布局、尺寸、控件形态一律不写，是为了不锁死新设计。
> 带伞判定已有一份更细的同风格说明：`docs/umbrella-decision-brief.md`，本文第 7 节只做摘要。

---

## 1. 要替用户回答的问题

产品的一句话：**按今天的天气、你为谁穿衣、你要做什么活动，算出你需要的穿衣结构，并告诉你此刻穿哪几层、什么时候脱。**

它拆成 5 个独立结论，它们各自由不同数据驱动、可信度不同：

| # | 用户的问题 | 系统的答案 | 驱动量 |
| --- | --- | --- | --- |
| Q1 | 今天需要怎样的**穿衣结构** | 贴身层 / 保暖层 / 防护层各是什么衣物，为什么 | 全天最坏时刻的六维需求 |
| Q2 | **此刻**穿哪几层 | 同一套结构里，此刻正穿哪几层、哪几层带着备用 | 当前一小时的热状态 + 当前雨况 |
| Q3 | 什么时候**脱 / 加** | 若干条"几点 脱某层 / 加某层"事件 | 逐时气温曲线 |
| Q4 | 今天出门**带不带伞** | 带伞 / 穿雨衣 / 不用带，以及被淋概率 | 通勤两段暴露窗口的降水概率 |
| Q5 | **明天**要留意什么 | 一句话（温差、降水、防寒防滑） | 明日与今日的差值 |

外加一条底线：**安全预警**（高温 / 严寒 / 大风 / 强降雨），它不是建议而是提醒，并且会强制改变 Q1 的需求。

**核心立场**：不是"多少度穿多少件"的查表，而是**先算身体需要什么（六维需求），再反推需要什么结构**。所以同一个 15℃，给怕冷的老人和怕热的年轻人骑车，答案不一样。

## 2. 产品硬约束（不可协商）

- **不用大模型**。结论必须由确定性算法从「天气数据 + 太阳数据 + 人群特征 + 活动强度 + 时间段 + 服装属性 + 可配置参数」算出。
- **不允许"温度区间 → 衣服"的映射表**。
- **同输入必同输出**，纯本地计算，穿搭计算零网络请求，断网可用。
- **文案与决策分离**：先出结构化结论，文字只是翻译，文字不参与判断。
- **纯前端应用，没有后端**。因此以下能力无法新增：推送通知、账号与多端同步、服务端历史、定时提醒。
- 界面语言简体中文；移动端优先、竖屏、触摸操作；可安装到主屏，离线可看上次快照。

## 3. 输入

### 3.1 位置（三选一，可失败）

| 途径 | 事实 |
| --- | --- |
| 城市搜索 | 中文关键词 → 最多 12 个候选城市 |
| 设备定位 | 先请求浏览器定位（5 秒超时，10 分钟内的旧定位直接复用）；**并发**发起 IP 定位兜底（城市级精度）；浏览器失败才用 IP 结果；两者都失败才报错 |
| 默认城市 | 上海（首次使用且未定位时） |

逆地理编码失败时，仍然可以只用经纬度出结论，此时城市名退化为"当前位置"。

### 3.2 天气数据（首次进入、手动刷新、换城市时各拉一次；一次覆盖今天 + 明天）

- **当前**：气温、体感、湿度、雨量、风速、风向、降水概率、天气现象、是否白天、云量。
- **今天逐时 24 条**：气温、湿度、风速、风向、雨量 mm/h、降水概率 %、天气现象、云量、UV 指数、短波辐射 W/m²、是否白天；太阳高度角由本地按日期与纬度计算。
- **今天 / 明天日级**：最高温、最低温、天气现象、日出、日落、全天雨量、全天最大降水概率、UV 峰值。

一条重要语义：**`-1` = 上游没给这项指标，不等于 0**。缺辐射时按太阳高度角和云量估算，缺逐时报文时整条曲线走合成估算（见 §10）。

### 3.3 用户设置（5 项，全部可持久保留）

| 项 | 取值 | 业务作用 |
| --- | --- | --- |
| 为谁穿衣 | 儿童 / 成人 / 老人 | 抬高"中性温度"→ 同样气温下需要更多保暖；儿童与老人还放大怕晒、并对高低温更保守 |
| 冷热体质 | 怕冷 / 标准 / 怕热 | 怕冷 +2.0℃、怕热 −1.5℃，直接作用于个体中性温度 |
| 今天主要活动 | 居家 / 办公 / 上课 / 步行 / 骑行 / 跑步 / 户外工作 / 户外休闲（8 类可选） | 代谢产热（抵消保暖）、自生风（骑行 4.0 m/s、跑步 3.0）、日晒与淋雨暴露系数、是否需要透气、单次户外时长 |
| 出门时刻 | `HH:mm`，**可空** | 带伞判定的第一段；影响早午晚分段边界 |
| 回家时刻 | `HH:mm`，**可空** | 带伞判定的第二段；可早于出门时刻（夜班，见 §10） |

模型里还定义了"驾车"（代谢 1.4、自生风 0.2、户外 4 分钟），但当前不在可选列表内。

### 3.4 服装目录

**45 件固定目录**（贴身上装 10 / 贴身下装 9 / 保暖层 13 / 防护层 13），不是用户自己的衣柜。每件衣物的全部属性：

| 属性 | 含义 | 量纲 |
| --- | --- | --- |
| 角色 | BASE 贴身 / INSULATION 保暖 / PROTECTION 防护 | 三选一 |
| 品类 | TOP 上装 / BOTTOM 下装 / OUTER 外层 | 三选一 |
| `insulationClo` | 热阻，参照 ISO 9920 | 0.06–1.20 clo |
| `wind` / `water` / `breathability` / `solar` | 防风 / 防水 / 透气 / 遮阳能力 | 各 0–1 |
| `weightGrams` | 重量 | 120–1300 g |
| `removable` | 是否便于穿脱携带 | 布尔 |
| `comfortRangeC` | 舒适温度窗口 | [最低, 最高] ℃ |
| `shellGrade` | 硬壳等级（仅外层） | 0–3，3 = 可防暴雨大风 |

## 4. 判断是怎么形成的

```
WeatherReport（24h 逐时 + 日级）
  ↓ 全天逐时热状态：作用温度 = 气温 + 辐射增益 − 风寒 + 湿度负载
  ↓ 个体修正（人群 + 体质 → 中性温度）、活动修正（代谢 / 自生风 / 暴露）
  ↓ 安全判定（先算）              → 只上调需求，永不下调
  ↓ 六维需求向量（0–100 × 6）     ★核心中间结果：今天的主要矛盾
  ↓ 层结构与槽位（最多 5 槽）
  ↓ 每槽从目录取前 4 候选 → 每槽定 1 件（两件保暖层不得同件）
  ↓ 组装 + 加权评分（0–100）      → 全天结构 dayOutfit
  ↓ 用"此刻"热状态决定 active     → 此刻穿几层 nowOutfit（同一套，不是两套）
  ↓ 时段三段 / 加减层时间线 / 配饰 / 带伞 / 明日一句话
= 一份完整结论
```

六条需要知道的判断规则（它们是产品的立身之本，改动会改变结论语义）：

1. **需求取全天最坏值**：保暖看最冷的一小时、防风看风最大的一小时、防雨看概率最高的全天值。因为产出是"全天要携带的一套"，不是"某一时刻的一套"。
2. **设计时刻 = 全天所需保暖最高的那一小时**。整套结构按它选配；午后变暖不是重配一套，而是从这套里脱掉某层。
3. **`dayOutfit` 与 `nowOutfit` 是同一套的两个状态**。层的 `active=false` 含义是"带着但此刻不穿"，不是"没推荐"。
4. **安全只上调**：极端天气把某维需求抬到下限值，绝不会因为"太热"就把保暖需求按安全名义压低（热天保暖本来就归零，由热模型负责）。
5. **层间保暖不可简单相加**：同层叠穿按 0.85 逐层递减；外层防风不足（<0.8）时整体有效保暖再打 0.85 折。
6. **每个结论都要能回溯到"因为什么"**：六维需求带触发说明、配饰带触发原因、带伞带成因码。（"这一层为什么存在"目前没落到输出里，见 §11。）

## 5. 六维需求向量（Q1 的输入）

每一维独立归一到 0–100（不做乘积放大），再与安全下限取 max。

| 维度 | 含义 | 由什么驱动 | 起始阈值 → 满值阈值 | 备注 |
| --- | --- | --- | --- | --- |
| WARMTH 保暖 | 需要多少热阻 | 全天最大"所需内在 clo" | 0.4 clo → 2.0 clo | 再减去活动代谢抵消（每 1 MET 超出静坐部分抵 0.25 clo） |
| WIND 防风 | 需要多少挡风 | 全天风速峰值 **+ 活动自生风** | 4 m/s → 12 m/s | 骑行/跑步自带风感，站着不动也冷 |
| RAIN 防雨 | 需要多少防水 | 全天降水概率 与 全天雨量，两者取大 | 概率 30%→85%；雨强 0.5→4 mm/h | 再乘活动的雨暴露系数（居家/办公为 0 → 全天有雨也不推防水） |
| BREATHABILITY 透气 | 需要多排汗散热 | 全天最热时段的作用温度 | 25℃ → 33℃ | 湿度 >70% 再 +15（湿热）；代谢 ≥3.5 MET 时不低于 45 |
| SOLAR 遮阳 | 需要多少防晒 | UV 指数 | UV 3 → UV 8 | 夜间为 0；再乘日晒暴露与人群怕晒系数 |
| REMOVABLE 可脱卸 | 需要多容易穿脱 | **昼夜温差** | 8℃ → 16℃ | 温差是核心输入，这是"洋葱式"的由来 |

安全触发的强制下限（只上调）：

| 触发 | 等级 | 强制抬升 |
| --- | --- | --- |
| 最高温 ≥35℃ | DANGER | 透气 ≥80、遮阳 ≥70 |
| 最高温 ≥33℃ | WATCH | 遮阳 ≥40 |
| 最低温 ≤−10℃ | DANGER | 保暖 ≥95 |
| 最低温 ≤−5℃ | WATCH | 保暖 ≥75 |
| 全天风速峰值 ≥15 m/s | DANGER | 防风 ≥90 |
| 全天风速峰值 ≥10 m/s | WATCH | 防风 ≥50 |
| 全天雨量 ≥8 mm | DANGER | 防雨 ≥95（外层务必防水） |
| 全天雨量 ≥4 mm | WATCH | 防雨 ≥60 |
| 儿童/老人 + 高温 | — | 透气 ≥60 |

安全等级取四条通道里的最高档，并各带一句预警文字。**强降雨只谈外层穿着，"带不带伞"是另一个模块单独给结论**，两处口径不混。

## 6. 层结构与选衣规则（Q1 的输出）

### 6.1 槽位规则（最多 5 个槽，顺序固定）

| 条件 | 产生 | 目标热阻下限 |
| --- | --- | --- |
| 恒定 | 贴身上装 + 贴身下装 | 0.03 clo |
| 保暖需求 > 12 | 1 个保暖层（上装） | 需求 ≤30→0.25、≤55→0.42、≤80→0.6、>80→0.8 |
| 保暖需求 > 45 | 第 2 个保暖层（上装） | 0.28 clo |
| 防雨 > 32 **或** 防风 > 32 | 1 个防护外层 | — |
| 上一个没触发，且遮阳 > 40 且保暖 < 50 | 1 个防晒外层 | — |

**推荐永远同时含上衣和下装**（分池挑选，避免只推上身）。不引入第 4 个层角色——要更厚就加第二个保暖槽。

### 6.2 硬约束（先过滤，不参与加权）

| 槽位要求 | 候选必须满足 | 组装时的复核门槛 |
| --- | --- | --- |
| 需要防水 | 防水 ≥0.85 | 防水 ≥0.9 |
| 需要防风 | 防风 ≥0.6 | 防风 ≥0.7 |
| 需要遮阳 | 遮阳 ≥0.8 | 遮阳 ≥0.8 |
| 有目标热阻 | `insulationClo` ≥ 槽位下限 | 同 |

硬约束不满足时退到该槽第二名单；确实没有可用衣物时不报错，而是给出一套"打了折"的结构。

### 6.3 拟合排序（每槽前 4 名）

- 保暖层：热阻越接近槽位目标越高（偏离 0.1 clo 扣 4 分）。
- 贴身层：热天透气主导、冷天热阻就近主导；贴身层只承担全身保暖的小份额（上装 0.05→0.35、下装 0.04→0.30 clo 随保暖需求线性）。
- 防护层：按需求侧重给防水/防风/遮阳加分。
- 通用：重量越轻加分越多，可脱卸随 REMOVABLE 加分。

### 6.4 组装结果与评分

一套结构给出的**可量化事实**：件名清单（分层）、名义 clo、有效 clo、整体防风/防水/透气/遮阳（各 0–1）、总重量 g、可脱卸件数、加权评分 0–100。

评分权重（合计 1.00）：保暖贴合 0.30、防风 0.15、防水 0.15、透气 0.15、轻量化 0.10、可脱卸 0.10、遮阳 0.05。
惩罚：防风需求 >50 而结构防风 <0.5 扣 25；防雨需求 >50 而防水 <0.5 扣 30；可脱卸需求 >60 而无可脱件扣 10。

### 6.5 此刻穿哪几层（Q2 的规则）

对同一套结构逐层判定 `active`：

| 层 | 判定 |
| --- | --- |
| 贴身层 | **始终穿** |
| 保暖层 | 当前作用温度 ≤ 该件舒适上界 +3℃ 时穿，否则"带着" |
| 防护层 | 今天有雨且此刻在下雨 → 穿；否则仅当作用温度 ≤12℃ 时穿，否则"带着" |

于是给出：此刻穿着的层数、层角色列表。

## 7. 带伞判定（Q4，摘要）

**它回答的不是"会不会下雨"，而是"值不值得为那十几分钟背一把伞"。**

- 把通勤建模成**两段户外暴露窗口**（出门段、回家段），单段时长按活动取值：步行 18 min、骑行 15、办公/上课/户外休闲 12、户外工作 10、跑步 8、开车 4、居家 3。
- 每段被淋概率 = 覆盖到的各小时降水概率按"该小时被窗口覆盖的比例 + 0.6 的降水持续度假设"折算后做 noisy-OR 合并。
- 两段合并 → 今天至少有一段被淋的概率 P，与阈值 **25%** 比较（阈值来自代价比"淋湿 : 白背 = 3 : 1"，是可调参数）。
- 结论三值：`SKIP` 不用带 / `BRING` 带伞 / `RAINCOAT` 改穿雨衣（段内风速 ≥12 m/s 或雨强 ≥8 mm/h 时伞失效）。
- 可信度两态：`HOURLY`（有逐时数据）/ `DEGRADED`（只能按全天概率，且结论不会比来源更有把握）。
- 结论**没有强度档**：概率再高也只是"带伞"，代码里不存在"强提醒"这一层（实测确认）。
- 未设置通勤时刻 → 按 07:30 / 18:00 估算并**必须告知**；两段都已过去（深夜）→ 改用"此刻起一段"；回家早于出门（夜班）→ 回家段落次日。

完整字段、12 个必覆盖状态、已知边界（含 4 条实测出来的数据缺失形状）见 `docs/umbrella-decision-brief.md`。

## 8. 时段 / 时间线 / 配饰 / 明日（Q3、Q5 与携带清单）

### 8.1 三段时段

- 默认：早 6–12、午 12–17、晚 17–24。
- 填了出门时刻 → 早段起点提前到该时刻（不晚于 10 点）；填了回家时刻 → 午段终点 = 回家前 4 小时（不早于 13 点）。
- 每段给出该段平均气温与一句定性说明。

### 8.2 加减层时间线（最多 6 条）

以 8–17 点中最暖的整点为锚：

| 事件 | 触发条件 |
| --- | --- |
| REMOVE 保暖层 | 存在保暖层时，在午间最暖点脱一层 |
| ADD 保暖层 | 最暖点之后、22 点前，出现比最暖点低 ≥4℃ 的整点 |
| ADD 防护层 | 今天有雨，时刻取"最暖点 +2 小时"与 17 点的较晚者 |

没有保暖层 / 没有雨 → 相应事件不出现（时间线可以为空）。

### 8.3 佩戴类配饰（8 类，阈值触发）

| 配饰 | 触发条件 |
| --- | --- |
| 围巾 | 全天最低 ≤4℃ |
| 手套 | 全天最低 ≤−2℃ |
| 暖手宝 | 全天最低 ≤−5℃ |
| 墨镜 + 遮阳帽 | 遮阳需求 >35 |
| 防晒霜 | 遮阳需求 >55 |
| 备用贴身衣 | 透气需求 >55（闷热出汗） |
| 轻便马甲 | 可脱卸 >45 且保暖 >20 |

**伞/雨衣不在此列**——那是"带不带"的携带决策，由 §7 单独测算，避免两处口径打架。

### 8.4 明日一句话

比较明日与今日：最低温变化 ≥3℃ 说升降、明日昼夜温差 ≥10℃ 提温差、降水概率 ≥30% 报概率、现象为雨/雷则提"记得带伞"、雪则提"防寒防滑"；全都不满足时给"变化不大"。明日的穿搭固定按 07:30 的通勤场景测算，不随用户设置的出门时刻变化。

## 9. 输出契约：可以拿来用的事实

一份结论包含以下**结构化事实**（字段名是当前契约，改呈现不需要改它们；需要新事实可提，属于工程侧扩展）：

**当下环境**：气温、体感、天气现象（晴/多云/雨/雪/雷/雾）、是否白天、湿度、风速、降水概率。

**热状态**：作用温度、体感、风寒降温量 K、湿度负载量 K、此刻所需内在 clo、设计时刻（第几小时）与该小时所需最大 clo。

**六维需求**：六个 0–100 数字 + 触发说明（该维达到强度才附带，中文句子）。

**全天结构**：分层列表（角色、该层衣物件名、是否此刻穿）、名义/有效 clo、防风/防水/透气/遮阳、总重量、可脱卸件数、加权评分。

**此刻**：正穿层数、正穿层角色、"带着但不穿"的层。

**携带**：配饰列表（种类 + 名称 + 触发原因码）。

**时间**：三段时段（边界 + 平均温 + 定性）、加减层事件（时刻 + ADD/REMOVE + 层名）。

**带伞**：见 §7 与 umbrella 专文。

**安全**：等级 NORMAL/WATCH/DANGER + 预警语句 + 被强制抬升的需求维度。

**明日**：一句话标题 + 一句说明。

**数据可信度元信息**（这些决定了"这句话能不能当真"，设计需要为它们准备表达）：
是否有逐时预报、数据生成时刻、距上次成功更新多少分钟、是否在用离线旧快照、是否已过期（>60 分钟）、数据源名称、通勤时刻是否为估算、带伞结论是 HOURLY 还是 DEGRADED。

## 10. 必须覆盖的状态（每一个都会真实发生）

**数据侧**

1. 冷启动且网络失败 → 没有任何数据，同时定位也可能失败。
2. 有旧快照但拉取失败 → 继续展示上次结果，并标注"这是 X 分钟前的、当前是离线状态"。
3. 快照超过 60 分钟 → 陈旧标记。
4. 上游没有逐时预报 → 全天曲线走**合成估算**：以当前气温为中心、15 点最暖 +6℃ / 3 点最凉 −6℃ 的正弦曲线，雨量为 0，辐射与 UV 用白天固定值；此时结论仍然要能出，并带估算说明。
5. 单个指标缺失（云量 / UV / 辐射 / 降水概率 = −1）→ 走估算，不得当作 0。
6. 逆地理失败 → 城市名是"当前位置"，经纬度可用。
7. 定位权限被拒 / 超时 / 系统定位服务关闭 → 三种情况提示不同（含去设置的指引）；IP 兜底成功时精度只有城市级，需要如实说明。
8. 城市搜索无结果。
9. 更换城市是**乐观更新**：城市立刻切换、旧天气先留着，新数据到达后替换——中间态存在"城市是新的、天气还是旧城的"。
10. 本地存储写失败（隐私模式等）→ 本次会话仍然可用，但下次进来配置会丢。

**判断侧**

11. 用户没设通勤时刻（结论按兜底时刻算，可信度下降）。
12. 只填了出门或只填了回家（半个日程）。
13. 夜班：回家时刻早于出门时刻，回家段落在次日，当日逐时数据不适用。
14. 深夜：两段通勤都已过去，改用"此刻起一段"。
15. 结论**在算法层面一天内会变**（已过去的通勤段被剔除），但它只在重新拉取数据或改设置时重算——**放着不动不会自己更新**（详见 §11）。
16. 同一份天气，换活动类型结论会变（步行 / 骑行 / 居家三套答案），且**不需要重新联网**——改设置只重算。
17. 高温高湿（33℃/85%）：不推保暖层，改推透气与备用贴身衣。
18. 大风降温：防风优先于加厚度（加再厚不挡风也没用）。
19. 全天有雨但用户是办公/居家（雨暴露系数 0）：**防雨需求可以是 0，但带伞判定仍然可能建议带伞**——两者口径本来就不同，这是最容易自相矛盾的地方。
20. 昼夜温差大（可脱卸高）：结构里出现两件保暖层，午后要脱一件。
21. 极端天气 DANGER / WATCH：提醒的强度要压过普通建议。
22. 降雪：算法只看降水量，降雪天可能仍输出"推荐带伞"（已知问题，见 §11）。
23. 时间线为空（没有保暖层、没有雨）——不是所有日子都有"几点脱"。
24. 配饰列表为空。

## 11. 已知边界（如果设计需要，可以反过来要求工程侧补）

- **服装目录是固定的 45 件，不是用户自己的衣柜**。推荐可能"对但不可执行"。用户衣橱是下一个版本的方向。
- 不做身高 / 体重 / 性别 / 体表面积建模，人群差异只由年龄档 + 冷热偏好覆盖。
- 单次户外暴露时长是写死的经验值，不来自真实导航数据；一天多次外出不支持。
- 降水概率是"这一小时下过雨"的概率，毛毛雨和暴雨同权，只有雨强字段能区分。
- 雪没有被独立建模；遮阳伞与带伞是两套东西，不混在同一个数字里。
- 淋湿代价阈值对所有人一样（不怕淋的人和怕淋的人同为 25%）。
- 早午晚分段用固定钟点（受通勤时间影响），**没有使用真实日出日落**；日出日落目前是数据字段。
- 缺逐时数据时，温度曲线是合成的 ±6℃ 估算，此时任何"全天最坏值"的精度都下降。
- 明日建议固定按 07:30 测算，不吃用户的出门时刻。
- **结论随时刻变化，但不会自己刷新**。算法层面"已过去的通勤段会被剔除"，可是当前实现只在重新拉天气或改设置时重算；挂着不动不会自动变。若设计需要"到了某个时刻自动更新结论"，属于工程侧要补的一环。
- 每槽只出 1 件定选 + 4 件候选池。**"这一层为什么存在"目前落不到结论里**：槽位原因有机器码（`NEED_INSULATION`、`NEED_RAIN_SHELL`、`NEED_SUN_SHELL` 等），但没有透出到输出；结论里的层只带衣物名和 active 标记，时段建议同理。如果需要逐层中文理由，属于工程侧要补的一环。
- 没有"昨天说了什么"的历史，也没有反馈学习（不会因为上次没带伞被淋了就调阈值）。

## 12. 明确不做（避免误扩范围）

时尚风格、色彩搭配、场合着装礼仪；穿搭社区 / UGC / 分享；服装电商与导购；对话式 AI 推荐；心率与健康数据驱动的动态建议；推送与定时提醒；账号与多端同步；多城市同时对比。

## 13. 需要设计判断的开放点

只标出这里确实要决策，不给答案：

- 五个结论（结构 / 此刻 / 时间线 / 带伞 / 明日）**谁是主、谁是次**？它们在算法里是并列的，而用户早上只有 30 秒。
- "带着但此刻不穿"这一层——它的价值全天最高（洋葱式的核心），也最容易被忽略。怎么让它"看得见但不干扰当下"。
- 概率 0（真没雨）与概率 0（没数据）如何区分；`SKIP 不用带`怎么表达才不会在下雨时让用户怪这个功能。
- 中间态数字（六维 0–100、clo、评分 0–100、风速 m/s、雨强 mm/h）该不该给普通用户看？给的话，谁能看懂、看懂了会改变什么行为。
- 安全预警（DANGER）要不要盖过穿搭建议的分量——它是提醒而不是建议，且会强制改变推荐结果。
- 需求的"全天最坏值"逻辑意味着：午后不冷但清晨冷 → 全天结构里始终有保暖层。怎么让用户理解"现在明明不冷，却让我带着毛衣"。
- 换城市/改活动后结论立刻变（不联网、瞬时重算）——要不要让用户感知到"这是刚按你选的条件重算的"。
- 引导用户填通勤时刻：什么时机、多强（这会显著改变带伞结论）。
- 第 10 节的 24 个状态，哪些值得独立设计，哪些可以合并成一句说明。
- 所有个性化输入都有默认值，一个都不选也能拿到结论；但选了会显著改变结论。第一次要不要索取输入、索取几项。
